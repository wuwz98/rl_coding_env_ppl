# RL Coding Env：公开材料、组成与数据量

核对日期：2026-09-24。模型家族只讨论下文明确注明的版本，不把一个版本的训练细节套用到其他版本。模型报告中的方法与数字是作者披露，本项目未独立复现实验。

## 1. 先确定要做哪种 coding 环境

| 类型 | Agent 实际做什么 | 常用验收 | 本项目安排 |
| --- | --- | --- | --- |
| 算法题 / 函数生成 | 从描述生成程序或函数 | 输入输出测试、时间/内存限制 | 可作训练器的简单预检，不能替代仓库任务 |
| 仓库级软件工程 | 读仓库、定位问题、编辑代码、运行测试、反复修复 | 问题测试 + 回归测试 | 第一版主线 |
| 终端工程任务 | 配环境、构建、调试、处理文件、运行服务 | 命令结果、文件/服务状态、功能检查 | 第二阶段扩展 |
| Web / 视觉开发 | 实现页面并通过浏览器交互 | 功能测试、截图、结构化视觉评分 | 后续扩展，验收成本较高 |

用户设想的 GitHub repo + issue 属于第二类。一个终端可以服务这些不同任务，但每类任务的正确性判据不同。

更适合直接研究“怎么构建 pipeline”的补充材料：

- [SWE-bench 数据字段](https://www.swebench.com/SWE-bench/guides/datasets/)：repo、base_commit、problem_statement、patch、test_patch、FAIL_TO_PASS、PASS_TO_PASS 等。
- [SWE-Factory](https://arxiv.org/abs/2506.10954)：自动化环境设置和问题验收，亦是 Step 3.5 引用的构建路线。
- [SWE-smith](https://arxiv.org/abs/2504.21798)：论文版本为 **50k 任务、128 仓库**，通过注入错误扩充任务；[资产说明](https://swesmith.com/getting_started/assets/)另列 **5k 专家轨迹**。三者分别是任务、仓库和轨迹。
- [SWE-rebench](https://arxiv.org/abs/2505.20411)：论文版本公开 **21k+ Python SWE 任务**；[V2 方法](https://arxiv.org/html/2602.23866v1)进一步展示多语言环境设置、结构化日志及修复前后执行流程。新版本规模与旧版本数字不要混用。

**从这些来源归纳：可靠执行反馈、环境可复现、任务多样性，以及模型与任务难度匹配，是本项目最应复现的部分。** 以下字段、阈值、预算和分期均为本项目设计建议，不声称是某一家公司的完整内部配方。

## 3. 一个 RL Coding Env 到底包括什么

可以把可交付任务理解为：

```text
任务说明 + 初始代码状态 + 执行环境 + 交互接口
         + 验证器/奖励 + 生命周期/资源限制 + 溯源信息
```

| 组成 | 最少要保存什么 | 为什么需要 |
| --- | --- | --- |
| Task / 任务 | problem_statement、语言、任务类型 | 明确要修复的行为及约束 |
| Initial state / 初态 | repo、准确 base_commit、源码快照摘要 | 保证每次从同一个 bug 状态开始 |
| Runtime / 运行时 | Dockerfile、依赖锁定、镜像 digest、OS/CPU 架构、安装脚本 | 历史版本在今天仍能运行 |
| Actions / 动作 | 执行命令、读写文件、提交结束的协议 | 模型能对环境产生改变 |
| Observations / 观察 | stdout、stderr、exit code、超时、截断信息 | 下一轮能根据真实反馈决策 |
| Verifier / 验证器 | 固定测试、测试 ID、解析器、隐藏验收资产 | 判断行为是否满足要求 |
| Reward / 奖励 | 成功条件、无效执行处理、奖励版本 | 将验收转成稳定学习信号 |
| Lifecycle / 生命周期 | reset、step、finish、close、终止原因、预算 | 可重复运行、并发隔离、可回收 |
| Provenance / 溯源 | issue/PR 链接、源码许可、采集时间、数据 split、构建日志 | 排查失败、去重及防止评测泄漏 |

另有三个相关但应分开的对象：

- **环境模板**：例如同一个 Python/依赖组合，可以承载多个任务。
- **Harness**：模型外的交互循环，负责拼接消息、调用工具、控制上下文和停止；不是训练算法。
- **Trajectory / rollout**：模型在某个任务上的一次执行记录；相同任务可生成多条轨迹。

Gold patch 是构建侧验证“此任务确实可解”的参考资产，不提供给解题 agent，也不要求模型逐字复现；测试通过的不同实现同样可以成功。没有 gold patch 的任务也能用于 RL，但初期很难验证任务及评分器是否可靠，暂不优先。

从 RL 角度，状态包含工作区、进程与预算；模型只能从工具结果看到局部状态；动作改变状态，终局验证给奖励。它通常更像部分可观察的交互任务。框架不必长成某个固定 Gym API，但必须具有可重置和隔离执行的语义。

## 4. 验证器是环境质量的核心

对于真实 PR 路线，记修复前代码为 B，参考源码补丁为 G，测试补丁为 T。

| 独立干净工作区 | 目的 | 应满足的条件 |
| --- | --- | --- |
| B + 原有测试 | 验证基础环境 | 项目测试可收集、可执行；MVP 要求原有测试通过 |
| B + T | 重现问题 | 至少一条与问题相关的测试稳定失败；不是缺包、测试收集失败或超时 |
| B + G + T | 验证参考解 | 问题测试转为通过，既有通过测试不回归 |
| B + Agent patch + T | 正式评分 | 同一套固定测试及资源规则下满足验收 |

F2P（FAIL_TO_PASS）指 B + T 失败、B + G + T 通过的**相同测试 ID**。P2P（PASS_TO_PASS）指两者都通过的测试。P2F 指原来通过、修复后失败的回归。此定义与 [SWE-smith 的验证说明](https://swesmith.com/guides/harnesses/)及上述 DeepSeek 流程相容。

本项目额外的质量门槛：

- B + T 和 B + G + T 各在全新环境重复 3 次，状态及测试 ID 一致。
- 无修改结果不能被判成功；缺失预期测试、全部 skip、零测试、解析失败都不能成功。
- 人工抽查测试是否覆盖 issue 的实际需求；必要时用错误补丁/变异补丁测试评分器。F2P 证明有区分能力，并不证明测试充分。
- 最终 grader 在新的隔离环境重放候选源码补丁，并注入自己持有的可信测试。不能读取 agent 自报的“测试通过”作为奖励。
- agent 环境仅有修复前快照和可见测试；不得残留 gold patch、未来提交、隐藏测试或包含参考答案的构建缓存。

首版采用可解释的二值奖励：

```text
基础设施故障 → status=infra_error，reward=null，单独重试/统计
无效候选补丁 / 缺失验收测试 / 候选执行失败 → reward=0
全部 F2P 通过 且 约定的 P2P 全通过 且 完整性检查通过 → reward=1
其他有效评测 → reward=0
```

基础设施是否故障应由受控预检、日志及必要的对照重跑确定；agent 引入语法错误、死循环或耗尽其任务预算是候选失败，不应被排除以抬高成功率。时间/token 成本先单独记录，后续再验证长度惩罚等 reward shaping 是否真的有益。

## 5. 一般要多少数据

不存在脱离基础模型、任务难度和训练预算的统一最低值。至少分别报告：

```text
仓库数 R
环境配置数 E（代码/依赖/平台版本）
独立任务数 N
每任务采样数 K
采样轮数 U
总 rollout 数、总生成 token、总执行时间和峰值并发 C
```

固定全集重复采样的简化预算：`rollouts = N × K × U`。实际在线训练会重采样和动态过滤，应以记录的真实次数为准。每道题改写 10 次不等于增加 10 个独立问题。

建议分期：

| 目标 | 建议独立任务量 | 仓库范围 | 可以支持的结论 |
| --- | --- | --- | --- |
| 验证构建闭环 | 3–5 | 1 个仓库 | 证明构建、验收、重置与采样能工作 |
| 面试 MVP | 30–100 | 3–5 个仓库 | 展示自动化产出漏斗、质量门槛、失败分类和基线 |
| 较完整项目 | 100–300 | 5–10 个仓库 | 比较筛选策略，初步观察跨仓库泛化 |
| 小规模 RL 研究 | 500–3,000 起步规划 | 增加仓库与 bug 类型 | 在足够算力下尝试稳定学习；不是最低要求或收益保证 |
| 前沿大规模训练 | 参照上面的已披露口径 | 多语言、多领域、多 harness | 公开资源规模不能用来反推完整训练预算 |

少量任务也能演示参数更新，但小样本训练曲线上升不代表泛化。几十条精确可重现、带质量证据的任务，对环境工程项目的说服力高于大量未经执行的 issue。

难度需结合目标模型试跑校准。初期每题 K=4 仅用于粗分桶，不能精确估计成功率。在独立采样、二值奖励的简化假设下，某题成功率 p、每组 K 条时，组内有成有败的概率为 `1 - p^K - (1-p)^K`。全成功或全失败的组没有来自该奖励的组内相对优势；GRPO 类训练因此不能只追求数据总量。应在保留整体难度分布的前提下补充可学习任务。

预算例子（假设，不是测量结果）：100 个任务 × 4 条 rollout × 1 轮 = 400 条轨迹。每条平均生成 8k token，则约 3.2M 生成 token；若每条占用环境 5 分钟，则约 33.3 容器小时，2 并发理想下约 16.7 小时。镜像构建、质检、评分、排队和失败重试另算。API 成本还包括每轮重传的历史输入、缓存计费和可能的推理 token，不能只按 3.2M 输出预算。

## 6. 面试中值得讲清楚的取舍

1. 为什么 PR-first：已有修复和测试，容易证明任务可解、奖励有区分度。
2. 为什么 clone 不够：源码历史与 GitHub issue/PR 的产品元数据是不同数据源。
3. 为什么先做 verifier：奖励错误会系统性地推动模型学错方向。
4. 为什么不一开始追求万级：先测最终有效产出率和每个合格任务成本。
5. 为什么拆三条流水线：环境生成、agent rollout、策略更新的故障和资源瓶颈不同。
6. 为什么预留 synthetic 路线：重复利用稳定环境降低扩容成本，但需单独报告真实与合成分布。
7. 为什么保留未见仓库评测：随机拆分同一个 issue 的变体会高估泛化。

若尚未训练，准确的项目表述是：“我构建了能给 coding agent 提供可信执行奖励的环境生成和采样 pipeline。”获得真实数据后再补充任务量、成功率及成本，不预填成绩。
